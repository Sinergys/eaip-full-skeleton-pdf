**Критичные недостающие данные:**

1. **Данные коммерческого учёта электроэнергии:**
   - Нужны детальные таблицы коммерческого учёта электроэнергии по Навои ИЭС за период энергоаудита (2024-2025) в Excel или CSV формате:
     - По месяцам/кварталам
     - По узлам учёта (трансформаторным подстанциям)
     - Активная и реактивная энергия отдельно

2. **Данные коммерческого учёта газа:**
   - Нужны полные данные коммерческого учёта газа за весь период энергоаудита (не только 1 квартал):
     - По месяцам/кварталам
     - Объёмы потребления (м³)
     - Возможно по точкам учёта

3. **Данные по расходу топлива:**
   - Нужны детальные таблицы расхода топлива по блокам/агрегатам ТЭС:
     - По видам топлива (газ, мазут и т.п.)
     - По периодам (месяцы/кварталы)
     - В числовом формате (Excel, CSV), а не только сканированные счёт-фактуры

4. **Архивы SCADA/DCS:**
   - Нужны архивы данных SCADA/DCS системы (если доступны) за период энергоаудита:
     - Параметры работы оборудования
     - Режимы работы блоков
     - Технологические параметры

5. **Данные по продукции (выработка энергии):**
   - Нужны данные по выработке электроэнергии и тепловой энергии:
     - По месяцам/кварталам
     - По блокам/агрегатам (если применимо)
     - В Excel или CSV формате

6. **Полный перечень оборудования:**
   - Нужен актуализированный перечень всего основного энергопотребляющего оборудования:
     - Электродвигатели (мощность, количество, цех)
     - Насосы (уже частично есть в KSB спецификациях)
     - Вентиляторы
     - Компрессоры
     - Трансформаторы
     - Другое оборудование

7. **Технологические схемы:**
   - Нужны актуальные технологические схемы систем:
     - Электроснабжения
     - Теплоснабжения
     - Газоснабжения
     - Водоснабжения
     - В электронном формате (CAD, PDF с возможностью векторного чтения)

### N3.3. Структура конвейера (этапы обработки)

В данном подпункте задаётся логическая структура конвейера обработки данных Навои от входных файлов до формирования энергопаспорта и отчёта. Конвейер связывает типы файлов (из N3.1) и маппинг на каноническую модель (из N3.2) с расчётами и формированием выходных документов по требованиям ПКМ-690. Описанные этапы определяют последовательность операций, которые должны быть реализованы в модулях импорта, валидации, расчётов и генерации отчётов EAIP.

#### Этап 1. Загрузка и парсинг файлов (Ingest/Parse)

**Источники (типы файлов из N3.1):**

- Все типы файлов из N3.1 (17 логических типов)
- Приоритетная обработка: "Акты балансов по месяцам" (149 файлов), "Данные коммерческого учёта электроэнергии" (Q1), "Данные коммерческого учёта газа" (Q2), "Данные по выработке/продукции" (Q4)

**Основные действия:**

- Загрузка файлов из директорий (`C:\AUDIT\OBJECTS\Navoiy IES`, включая подкаталоги)
- Определение типа файла по имени, пути, содержимому (сопоставление с типами из N3.1)
- Парсинг содержимого файлов:
  - Excel-файлы (.xls, .xlsx, .xlsm): извлечение данных из листов, парсинг таблиц с учётом структуры актов балансов, отчётов, перечней оборудования
  - Word-файлы (.docx): извлечение структурированных данных из таблиц, текстовых блоков
  - PDF-файлы: OCR для сканированных документов, извлечение текста из векторных PDF
- Нормализация данных: приведение единиц измерения, дат, числовых значений к единому формату
- Извлечение метаданных: определение периодов (годы, кварталы, месяцы), идентификация ресурсов, продукции, оборудования

**Результат этапа:**

- Структурированные данные в промежуточном формате (JSON или внутренние структуры данных), готовые для записи в каноническую модель
- Метаданные о файлах: типы данных, периоды, соответствие типам из N3.1
- Связь между данными из разных файлов (например, акты балансов за разные месяцы)

**Задействованные сущности (подготовка):**

- Данные подготавливаются для заполнения: Enterprise, EnergyAuditProject, Period, Product, EnergyResource, Meter, Normative, Site/Building

#### Этап 2. Запись в каноническую модель (Persist/Canonicalize)

**На входе:**

- Структурированные данные из Этапа 1 (парсинг)
- Информация о предприятии Навои ИЭС
- Метаданные о типах файлов и периодах

**Задействованные сущности канонической модели:**

- **Enterprise:** Создание/обновление записи предприятия "Навои ИЭС"
- **EnergyAuditProject:** Создание проекта энергоаудита для выбранного года (2024-2025)
- **Period:** Создание периодов (год, кварталы, месяцы) для проекта
- **EnergyResource:** Наполнение справочника энергоресурсов (электроэнергия, газ, тепло, ГСМ и т.п.)
- **Product:** Создание записей о продукции (выработка электроэнергии, тепловой энергии)
- **Meter:** Создание записей об узлах учёта (трансформаторные подстанции, точки учёта газа)
- **MeterReading:** Запись показаний узлов учёта по периодам (из коммерческого учёта электроэнергии и газа)
- **Site/Building:** Создание записей о площадках/зданиях (из перечней оборудования, проектной документации)
- **Normative:** Запись нормативных показателей с привязкой к ресурсам и продукции
- **EnergyConsumption:** Запись фактического потребления энергоресурсов (из актов балансов, коммерческого учёта)
- **ProductVolume:** Запись объёмов продукции по периодам (из файлов реализации/выработки)

**Основные действия:**

- Маппинг данных из Этапа 1 на сущности канонической модели по таблице маппинга N3.2
- Создание/обновление записей Enterprise и EnergyAuditProject
- Создание иерархии периодов (год → кварталы → месяцы) для проекта
- Наполнение справочника EnergyResource (если не заполнен ранее)
- Извлечение данных о продукции из файлов "Данные по выработке/продукции": создание записей Product и ProductVolume
- Извлечение данных о узлах учёта: создание записей Meter и MeterReading из файлов коммерческого учёта
- Запись нормативов: создание записей Normative из файлов "Нормативные показатели"
- Запись энергопотребления: создание записей EnergyConsumption из актов балансов и коммерческого учёта
- Заполнение категорий потребления: структурирование EnergyConsumption.by_usage (production, losses, household) из файлов по потерям и хозяйственным нуждам
- Привязка данных к периодам: связывание всех записей с соответствующими Period

**Результат этапа:**

- Все входные данные преобразованы и записаны в каноническую модель EAIP
- Сущности связаны между собой (Enterprise → EnergyAuditProject → Period → EnergyConsumption, Product, Meter и т.д.)
- Данные готовы для валидации и расчётов

**Порядок обработки типов файлов:**

1. Справочные данные: Enterprise, EnergyResource (если не заполнены)
2. Структурные данные: EnergyAuditProject, Period, Site/Building
3. Данные о продукции: Product, ProductVolume (из файлов выработки)
4. Данные об учёте: Meter, MeterReading (из коммерческого учёта)
5. Нормативы: Normative (из нормативных показателей)
6. Фактическое потребление: EnergyConsumption (из актов балансов)

#### Этап 3. Валидация и проверки (Validate)

**На входе:**

- Заполненная каноническая модель из Этапа 2
- Эталонные данные (если есть): "Сводные балансы и отчёты", "Готовые энергопаспорта"

**Задействованные сущности:**

- Все сущности из Этапа 2 (Enterprise, EnergyAuditProject, Period, EnergyConsumption, Product, Meter, Normative и т.д.)

**Основные действия:**

- **Проверка полноты данных:**
  - Наличие критичных типов данных (акты балансов, коммерческий учёт, выработка)
  - Наличие данных за требуемые периоды (2024-2025 для энергоаудита)
  - Проверка обязательных связей (проект → периоды, ресурсы → потребление, продукция → объёмы)

- **Балансовые проверки:**
  - Согласованность данных между актами балансов и коммерческим учётом (валидация через MeterReading)
  - Согласованность сумм по периодам (месяцы → кварталы → год)
  - Согласованность потребления по категориям (production + losses + household + own_needs = total)

- **Логические проверки:**
  - Корректность единиц измерения и их соответствие EnergyResource.unit_main
  - Корректность периодов (даты в допустимых пределах)
  - Положительность значений потребления, объёмов продукции (где применимо)

- **Валидация против эталонов:**
  - Сравнение агрегированных данных с "Сводными балансами и отчётами" (если доступны)
  - Выявление расхождений между расчётными и эталонными значениями

- **Проверка готовности к расчётам:**
  - Наличие данных для всех семи подсистем логики энергопаспорта
  - Наличие нормативов для сравнения "факт/норма"
  - Наличие продукции для расчёта удельных показателей

**Результат этапа:**

- Отчёт о валидации: список проверок, предупреждений, ошибок
- Индикация недостающих данных (с привязкой к запросам Q1–Q14 из N2.2)
- Подтверждение готовности данных к расчётам или список блокирующих проблем

**Критичные проверки:**

- Для подсистемы "Энергетический баланс": наличие EnergyConsumption по всем ресурсам за требуемые периоды
- Для подсистемы "Удельные показатели": наличие Product, ProductVolume и Normative
- Для подсистемы "Структура потребления": наличие данных по категориям (потери, хоз-быт)

#### Этап 4. Расчёты ключевых показателей (Calculate)

**На входе:**

- Валидированные данные из канонической модели (Этап 3)
- Справочники: EnergyResource (с коэффициентами k_tut), Normative

**Задействованные сущности:**

- **Входные:** EnergyAuditProject, Period, Product, ProductVolume, EnergyConsumption, MeterReading, Normative, EnergyResource, Site/Building
- **Выходные (результаты расчётов):** EnergyConsumption (расчётные значения), EnergyBalanceRow, SpecificIndicator, Dynamics

**Основные действия (по семи подсистемам логики энергопаспорта, ТЗ 4.6):**

1. **Подсистема "Продукция":**
   - Агрегация объёмов продукции (ProductVolume) по периодам (месяцы → кварталы → год)
   - Результат: агрегированные объёмы продукции в Product/ProductVolume

2. **Подсистема "Нормы и фактический удельный расход":**
   - Связывание фактического потребления (EnergyConsumption) с нормативами (Normative)
   - Расчёт фактических удельных расходов: потребление / объём продукции
   - Результат: запись в EnergyConsumption и подготовка данных для SpecificIndicator

3. **Подсистема "Энергопотребление по видам продукции":**
   - Распределение потребления (EnergyConsumption) по видам продукции (Product)
   - Использование нормативов и фактических данных для распределения
   - Результат: обновление EnergyConsumption с привязкой к продукции

4. **Подсистема "Структура энергопотребления предприятия":**
   - Агрегация потребления по категориям (production, losses, household, own_needs)
   - Распределение по категориям на основе данных из файлов "Данные по потерям" и "Данные по хозяйственным нуждам"
   - Результат: обновление EnergyConsumption.by_usage для всех записей

5. **Подсистема "Энергетический баланс":**
   - Агрегация потребления по всем энергоресурсам (EnergyConsumption) с пересчётом в т.у.т. через EnergyResource.k_tut
   - Формирование строк баланса по категориям (production, losses, household, own_needs)
   - Результат: создание записей EnergyBalanceRow для каждого периода с балансовыми данными в т.у.т.

6. **Подсистема "Удельные показатели":**
   - Расчёт удельных показателей на единицу продукции: EnergyConsumption / ProductVolume
   - Расчёт удельных показателей на площадь: EnergyConsumption / Site.area_m2 (если доступно)
   - Сравнение с нормативами: расчёт отклонений "факт/норма"
   - Результат: создание записей SpecificIndicator с actual_value, normative_value, deviation_abs, deviation_percent

7. **Подсистема "Динамика удельных показателей":**
   - Сравнение показателей между несколькими проектами (годами) при наличии данных за несколько лет
   - Расчёт трендов и изменений между годами
   - Результат: создание записей Dynamics с years_data, trend, changes

**Результат этапа:**

- Все расчётные сущности заполнены: EnergyBalanceRow, SpecificIndicator, Dynamics
- EnergyConsumption дополнена расчётными значениями и структурой по категориям
- Данные готовы для формирования энергопаспорта и отчёта

**Зависимости между подсистемами:**

- Подсистемы 1–3 (Продукция, Нормы, Потребление по продукции) должны быть выполнены перед подсистемой 6 (Удельные показатели)
- Подсистема 4 (Структура потребления) должна быть выполнена перед подсистемой 5 (Энергетический баланс)
- Подсистема 6 (Удельные показатели) должна быть выполнена перед подсистемой 7 (Динамика)

#### Зависимости и блокирующие факторы

**Зависимости между этапами:**

1. **Этап 2 блокируется Этапом 1:**
   - Запись в каноническую модель возможна только после успешного парсинга файлов
   - Отсутствие парсера для конкретного типа файла блокирует запись данных этого типа

2. **Этап 3 блокируется Этапом 2:**
   - Валидация требует наличия данных в канонической модели
   - Частичная валидация возможна, но полная проверка готовности к расчётам требует завершения записи критичных данных

3. **Этап 4 блокируется Этапом 3:**
   - Расчёты выполняются только после валидации и подтверждения готовности данных
   - Отсутствие критичных данных (обнаруженное на Этапе 3) блокирует соответствующие подсистемы расчётов

4. **Этап 5 блокируется Этапом 4:**
   - Формирование энергопаспорта и отчёта требует наличия расчётных показателей (EnergyBalanceRow, SpecificIndicator)
   - Отсутствие результатов расчётов блокирует генерацию соответствующих разделов документов

**Зависимости по данным:**

- **Для подсистемы "Энергетический баланс":** требуется EnergyConsumption по всем ресурсам → зависит от загрузки "Актов балансов" и "Коммерческого учёта" (Q1, Q2)
- **Для подсистемы "Удельные показатели":** требуется Product, ProductVolume, Normative → зависит от загрузки "Данных по выработке" (Q4) и "Нормативных показателей" (Q8)
- **Для подсистемы "Структура потребления":** требуется распределение по категориям → зависит от "Данных по потерям" и "Хозяйственным нуждам" (Q7)
- **Для подсистемы "Динамика":** требуется наличие данных за несколько лет → зависит от загрузки исторических данных (Q9)

**Что можно выполнить уже сейчас (при текущем наборе данных из N1/N1R/N1R.4):**

1. **Этап 1 (частично):** Парсинг доступных типов файлов:
   - Акты балансов (149 файлов, 2020-2025) — можно парсить
   - Перечни оборудования (НТЭС.docx, спецификации KSB) — можно парсить
   - Ежемесячные отчёты (xisoboti, 35 файлов) — можно парсить
   - Нормативные показатели (10 файлов) — можно парсить
   - Данные по выработке (Реализация 2022-2025, 5 файлов) — можно парсить

2. **Этап 2 (частично):** Запись в каноническую модель:
   - Enterprise, EnergyAuditProject, Period — можно создать
   - Product, ProductVolume (из файлов реализации) — можно заполнить
   - Normative (из нормативных показателей) — можно заполнить
   - EnergyConsumption (из актов балансов) — можно частично заполнить
   - Site/Building (из перечней оборудования) — можно частично заполнить

3. **Этап 3 (частично):** Валидация:
   - Проверка полноты загруженных данных — можно выполнить
   - Балансовые проверки по доступным данным — можно выполнить
   - Выявление недостающих данных (Q1–Q14) — можно зафиксировать

4. **Этап 4 (частично):** Расчёты:
   - Подсистема "Продукция" — можно выполнить (есть ProductVolume)
   - Подсистема "Нормы и фактический удельный расход" — можно частично выполнить (есть Normative, частично EnergyConsumption)
   - Подсистема "Энергетический баланс" — можно частично выполнить (есть акты балансов, но не все ресурсы/периоды)
   - Подсистема "Удельные показатели" — можно частично выполнить (зависит от полноты EnergyConsumption и Normative)

5. **Этап 5 (частично):** Формирование представлений:
   - Можно заполнить части энергопаспорта, где есть данные
   - Нельзя полностью заполнить без результатов всех подсистем расчётов

**Что явно зависит от получения недостающих данных (Q1–Q14, N2.2):**

1. **Заблокировано запросами Q1–Q2:** Полноценный расчёт энергобаланса по газу и полный коммерческий учёт электроэнергии требуют данных Q1 (все узлы учёта) и Q2 (коммерческий учёт газа за полный период)

2. **Заблокировано запросом Q4:** Полный расчёт удельных показателей требует данных Q4 (выработка энергии за период энергоаудита 2024-2025, по всем блокам)

3. **Заблокировано запросом Q7:** Полная структура потребления по категориям требует данных Q7 (детализация по категориям: производство, потери, хоз-быт)

4. **Заблокировано запросом Q8:** Сравнение "факт/норма" требует нормативов Q8 (актуальные нормативные показатели для периода энергоаудита)

5. **Заблокировано запросом Q10:** Экономическое обоснование мероприятий в плане энергосбережения требует тарифов Q10 (тарифы на энергоресурсы)

6. **Заблокировано запросами Q5, Q9:** Расширенный анализ режимов работы и динамика показателей требуют данных Q5 (SCADA/DCS архивы) и Q9 (данные за несколько лет для динамики)

**Критический путь конвейера:**

Для базового энергопаспорта и отчёта по ПКМ-690 критический путь включает:
1. Загрузка актов балансов (доступно) + коммерческий учёт (Q1, Q2) → EnergyConsumption
2. Загрузка выработки (Q4) → Product, ProductVolume
3. Загрузка нормативов (Q8) → Normative
4. Загрузка структуры потребления (Q7) → EnergyConsumption.by_usage
5. Расчёт энергобаланса → EnergyBalanceRow
6. Расчёт удельных показателей → SpecificIndicator
7. Формирование энергопаспорта и отчёта

- **Ежемесячные отчёты по потреблению (xisoboti)** (2023-2024, 35 файлов): коммерческий учёт потребления электроэнергии по месяцам с детализацией по системам/цехам. Универсальный тип данных — ежемесячные отчёты по коммерческому учёту применяются на любых предприятиях.

- **Данные коммерческого учёта электроэнергии (узлы учёта)** (2021-2024, данные по узлу 10.30 и др.): активная и реактивная энергия по узлам учёта (трансформаторные подстанции). Универсальный тип данных — учёт по узлам применяется на любых предприятиях с несколькими точками учёта.

- **Данные коммерческого учёта газа** (2022-2024, 19 файлов): объёмы потребления газа (м³), акты поставки, коммерческий и технический учёт по точкам/блокам. Универсальный тип данных — коммерческий учёт газа применяется на предприятиях, использующих газовое топливо.

- **Данные по выработке/продукции (реализация)** (2022-2025, 5 файлов): выработка электроэнергии и тепловой энергии по блокам/агрегатам. Универсальный тип данных — данные по продукции применяются на любых производственных предприятиях (для ТЭС продукция = выработка энергии).

Универсальный тип данных — перечни оборудования используются на любых предприятиях для структуризации потребления.

- **Данные по потерям энергии** (2023-2025, 6 файлов): потери тепловой энергии в теплосети, потери электроэнергии. Универсальный тип данных — данные по потерям применяются на любых предприятиях для структуры потребления по категориям.

- **Сводные балансы и отчёты** (2022-2025, 8 файлов): сводные энергетические балансы за периоды, утверждённые балансы для валидации. Универсальный тип данных — сводные балансы используются на любых предприятиях для проверки согласованности расчётов.

**Общая статистика:** Всего выявлено около 621 файл, из них ~560 новых (не учтённых в первоначальной инвентаризации N1/N1R.1). Цель — составить конкретную и воспроизводимую карту того, какие группы сканов должны обрабатываться OCR-модулем, какие поля извлекать, в какие сущности канонической модели загружать данные, и какие блокируемые показатели (N3.5) закроются при успешной оцифровке. Раздел также описывает детализированный процесс обработки (предобработка → OCR → постобработка → верификация → загрузка) и определяет приоритетную очередь оцифровки. Все выводы опираются только на существующие документы проекта (ТЗ, архитектура, аналитика N1R.4, N3.5, N4.1, N3.SUM, каноническая модель из `docs/EAIP_CORE_IMPLEMENTATION_PLAN.md`). Предположения о содержимом сканов явно помечаются как "предположительно" и обосновываются по имени файла/контексту.

**Ограничения:** Данный раздел является аналитическим и не предполагает реализации OCR или изменения ТЗ. Он формирует основу для планирования работ по оцифровке сканов в будущем.

#### N4.2.2. Детализированный процесс обработки сканов (предобработка → OCR → постобработка → верификация → загрузка)

Процесс обработки сканов опирается на требования из ТЗ (`docs/EAIP_TZ.md`, разделы 3.2.4 и 4.4) и архитектуру системы (`docs/EAIP_ARCHITECTURE.md`). Описание каждого этапа включает конкретные операции, инструменты/методы и метрики контроля качества.

##### Этап 1. Предобработка изображений

**Цель:** Улучшение качества изображений перед OCR для повышения точности распознавания текста и таблиц.

**Операции (согласно ТЗ 4.4.1):**
- Выравнивание изображения (deskew) — устранение перекоса отсканированных страниц
- Улучшение контраста — увеличение различия между текстом и фоном
- Улучшение резкости — повышение чёткости текста
- Бинаризация — преобразование в чёрно-белое изображение (при необходимости)
- Удаление шума — устранение артефактов сканирования
- Нормализация освещения — выравнивание яркости по странице
- Обрезка полей — удаление пустых областей для фокусировки на содержимом

**Инструменты/варианты:**
- Библиотека `PIL/Pillow` для базовых операций (контраст, резкость, бинаризация)
- Библиотека `scikit-image` для продвинутой предобработки (deskew, удаление шума)
- Специализированные модули улучшения изображений (согласно архитектуре: `image_enhancement.py`)

**Метрики контроля качества:**
- Визуальная проверка качества изображения после предобработки
- Измерение контраста (должен быть выше порога, например >50)
- Проверка отсутствия перекоса (угол наклона < 1 градуса)

**Ссылка на ТЗ:** `docs/EAIP_TZ.md`, раздел 4.4.1: "Предобработка изображений для улучшения качества распознавания"

---

##### Этап 2. OCR (распознавание текста)

**Цель:** Извлечение текста и структуры документа из отсканированных изображений.

**Операции (согласно ТЗ 3.2.4 и 4.4.1):**
- Распознавание текста из PDF-сканов
- Распознавание текста из изображений (JPG, PNG, TIFF)
- Определение структуры документа (заголовки, таблицы, текст)
- Извлечение табличных данных с сохранением структуры таблиц

**Инструменты/варианты:**
- **Tesseract OCR** (основной вариант, согласно ТЗ 4.4.1: "Использование современных методов OCR (Tesseract, коммерческие решения, AI-модели)")
- **Коммерческие OCR-решения** (опционально, для повышения точности)
- **AI-модели** (DeepSeek Vision API или аналоги, согласно архитектуре и коду `ai_parser.py`)
- **Специализированные табличные парсеры** (pdfplumber, camelot) для извлечения таблиц из OCR-текста

**Метрики контроля качества:**
- Confidence score для каждого распознанного символа/слова (порог по умолчанию: 60% для чисел, 70% для текста)
- Количество распознанных символов на страницу (должно быть >100 для текстовых страниц)
- Проверка наличия структурированных данных (таблицы, даты, числа) в распознанном тексте

**Ссылка на ТЗ:** `docs/EAIP_TZ.md`, раздел 3.2.4: "Применение OCR для распознавания текста из: PDF-сканов; изображений (JPG, PNG); сканов таблиц и счётчиков"

---

##### Этап 3. Структурирование данных

**Цель:** Преобразование распознанного текста в структурированный формат, готовый для загрузки в каноническую модель EAIP.

**Операции (согласно ТЗ 4.4.2):**
- Идентификация таблиц в документе
- Извлечение данных из таблиц
- Определение структуры документа (заголовки, разделы, даты)
- Нормализация единиц измерения (приведение к каноническим единицам из EnergyResource)
- Преобразование в каноническую модель EAIP

**Инструменты/варианты:**
- **Регулярные выражения** для извлечения структурированных полей (даты, числа, единицы измерения)
- **Табличные парсеры** (pdfplumber, camelot) для извлечения таблиц с сохранением структуры
- **AI-модели** для понимания структуры документа и извлечения семантических полей (согласно коду `ai_parser.py`)
- **Правила парсинга** для каждого типа документа (счёт-фактуры, нормативы, акты)

**Метрики контроля качества:**
- Количество успешно извлечённых полей из каждого документа (должно быть >50% от ожидаемых полей)
- Корректность извлечённых единиц измерения (соответствие справочнику EnergyResource)
- Сохранение структуры таблиц (количество строк/столбцов соответствует оригиналу)

**Ссылка на ТЗ:** `docs/EAIP_TZ.md`, раздел 4.4.2: "Выделение и структурирование табличных данных: идентификация таблиц в документе; извлечение данных из таблиц; преобразование в каноническую модель EAIP"

---

##### Этап 4. Выявление сомнительных фрагментов

**Цель:** Автоматическое выявление данных с низкой уверенностью распознавания или логическими противоречиями для последующей ручной верификации.

**Операции (согласно ТЗ 4.4.2 и 4.4.3):**
- Маркировка данных с низкой уверенностью распознавания (ниже порога)
- Выявление логических противоречий (суммы не сходятся, отрицательные значения, значения вне допустимых диапазонов)
- Проверка соответствия ожидаемым форматам данных (даты, числа, единицы измерения)
- Выявление несоответствий между связанными данными (например, дата поставки позже даты счёт-фактуры)

**Инструменты/варианты:**
- **Пороги уверенности OCR** (настраиваемые, согласно ТЗ 4.4.3): порог для маркировки сомнительных данных, разные пороги для разных типов данных (числа: 60%, текст: 70%, даты: 80%)
- **Правила валидации** (логические проверки): суммы, диапазоны, форматы (согласно ТЗ 4.4.3)
- **AI-модели** для выявления аномалий и противоречий

**Метрики контроля качества:**
- Процент данных, помеченных как сомнительные (должен быть <30% для качественных сканов)
- Количество выявленных логических противоречий
- Точность выявления ошибок (false positive rate <10%)

**Ссылка на ТЗ:** `docs/EAIP_TZ.md`, раздел 4.4.2: "Выявление сомнительных фрагментов: низкая уверенность распознавания (ниже порога); логические противоречия (суммы не сходятся, отрицательные значения и т.п.); несоответствие ожидаемым форматам данных"

---

##### Этап 5. Подготовка пометок для ручной проверки

**Цель:** Подготовка интерфейса для ручной верификации аудитором сомнительных данных и исправления ошибок.

**Операции (согласно ТЗ 3.2.5 и 4.4.2):**
- Подсветка сомнительных значений в интерфейсе
- Комментарии с указанием причины сомнения (низкая уверенность OCR, логическое противоречие, несоответствие формату)
- Рекомендации по исправлению (предложения от AI, если доступны)
- Отображение оригинального изображения рядом с распознанными данными для визуальной проверки

**Инструменты/варианты:**
- **Веб-интерфейс** для просмотра распознанных данных с пометками (согласно ТЗ 3.2.5: "Просмотр распознанных данных с пометками о сомнительных значениях")
- **AI-подсказки** для предложения исправлений (согласно ТЗ 3.2.5: "Получение подсказок от ИИ: предложения по исправлению ошибок")
- **Интерактивное редактирование** полей прямо в интерфейсе

**Метрики контроля качества:**
- Время верификации одного документа (целевой показатель: <10 минут на счёт-фактуру)
- Процент данных, исправленных аудитором (должен быть <20% для качественных сканов)
- Удобство интерфейса (субъективная оценка аудитора)

**Ссылка на ТЗ:** `docs/EAIP_TZ.md`, раздел 4.4.2: "Подготовка пометок для ручной проверки: подсветка сомнительных значений в интерфейсе; комментарии с указанием причины сомнения; рекомендации по исправлению"

---

##### Этап 6. Загрузка в каноническую модель

**Цель:** Преобразование верифицированных структурированных данных в сущности канонической модели EAIP и запись в базу данных.

**Операции:**
- Маппинг извлечённых полей на атрибуты сущностей канонической модели (согласно таблице N4.2.1)
- Создание/обновление записей Enterprise, EnergyAuditProject, Period (если необходимо)
- Создание/обновление записей EnergyResource, Product, Meter (если необходимо)
- Запись данных потребления в EnergyConsumption
- Запись нормативов в Normative
- Запись тарифов (если есть сущность Tariff, или через EnergyResource.metadata)
- Связывание записей с периодами (Period)

**Инструменты/варианты:**
- **ORM (SQLAlchemy или аналог)** для работы с базой данных
- **Маппинг-правила** для преобразования структурированных данных в сущности (согласно таблице N3.2)
- **Валидация данных** перед записью (проверка обязательных полей, связей)

**Метрики контроля качества:**
- Количество успешно загруженных записей (должно быть >90% от верифицированных данных)
- Корректность связей между сущностями (все foreign keys валидны)
- Полнота данных (все обязательные поля заполнены)

**Ссылка на ТЗ:** `docs/EAIP_TZ.md`, раздел 3.2.4: "Структурирование распознанных данных в каноническую модель EAIP"

**Формат структурированных выходных данных:**

Структурированные данные после OCR и верификации должны быть представлены в формате JSON, готовом для загрузки в каноническую модель:

#### N4.2.3. Приоритеты оцифровки (H/M/L) с обоснованием

**Критичный приоритет (H — высокий):**

1. **Сканированные счёт-фактуры (31 файл)** — приоритет H
   - **Обоснование:** Закрывают критичные запросы Q2 (коммерческий учёт газа), Q3 (расход топлива), Q10 (тарифы), Q11 (стоимость оборудования). Эти данные необходимы для формирования полного энергобаланса по газу (N3.5), энергетического баланса по видам топлива (N3.5) и экономических показателей мероприятий (N3.5). Без этих данных невозможно выполнить требования ПКМ-690 по энергобалансу и плану мероприятий.

2. **Сканированные нормативные документы (1 файл)** — приоритет H
   - **Обоснование:** Критично для Q8 (нормативные показатели). Без нормативов невозможно рассчитать отклонения "факт/норма" и оценить энергоэффективность предприятия. Это блокирует показатели "Удельные показатели за период энергоаудита" и "Отклонения факт/норма" (N3.5), что делает невозможным заполнение раздела энергопаспорта "Удельные показатели".

3. **Сканированные документы по потерям (1 файл)** — приоритет H
   - **Обоснование:** Критично для Q7 (структура потребления по категориям). Структура потребления по категориям обязательна по ПКМ-690 (производство, потери, хоз-быт, собственные нужды). Блокирует показатель "Структура потребления по категориям (ПКМ-690)" (N3.5), что делает невозможным корректное заполнение раздела энергобаланса.

**Средний приоритет (M):**

4. **Сканированные акты выполненных работ (14 файлов)** — приоритет M
   - **Обоснование:** Важно для Q11 (стоимость оборудования) и Q12 (данные для экономического анализа), но не критично для базового энергобаланса. Эти данные улучшают экономическое обоснование мероприятий, но не блокируют основные расчёты.

5. **Сканированные прогнозные документы (2 файла)** — приоритет M
   - **Обоснование:** Могут дать ориентировочные данные для Q4 (выработка) и Q9 (динамика), но не заменяют фактические данные. Прогнозы полезны для предварительных оценок, но не являются обязательными для формирования энергопаспорта.

**Низкий приоритет (L):**

6. **Проектная документация (88 файлов)** — приоритет L
   - **Обоснование:** Полезна для Q6 (технологические схемы) и понимания структуры систем, но не критична для базовых расчётов энергобаланса. Большинство проектной документации — схемы, а не таблицы с данными, поэтому OCR менее эффективен.

7. **Готовый энергопаспорт (1 файл)** — приоритет L
   - **Обоснование:** Используется только как эталон структуры, не является источником данных для расчётов.

#### N4.2.4. Изменения в канонической модели после загрузки данных из сканов

После успешной оцифровки сканов и загрузки данных в каноническую модель EAIP будут дополнены следующие сущности (согласно канонической модели из `docs/EAIP_CORE_IMPLEMENTATION_PLAN.md`, разделы 4.1–4.9):

1. **EnergyConsumption** (Энергопотребление):
   - Заполнение `consumption_main_unit` из счёт-фактур по газу (объёмы поставки в м³)
   - Заполнение `cost` из счёт-фактур (стоимость потребления в суммах)
   - Заполнение `by_usage` (JSON: {production, losses, household, own_needs}) из документов по потерям и структуре потребления

2. **MeterReading** (Показания узлов учёта):
   - Создание записей показаний по точкам учёта газа из счёт-фактур (объёмы, даты, номера точек учёта)
   - Связывание с сущностью Meter и Period

3. **Normative** (Нормативы):
   - Создание записей нормативов из сканированных нормативных документов (value, unit, source, valid_from, valid_to)
   - Связывание с EnergyResource и Product (если норматив по продукции)

4. **EnergyResource** (Энергоресурсы):
   - Дополнение метаданных о тарифах (через `metadata` JSON или расширение модели сущностью Tariff)
   - Тарифы из счёт-фактур по газу (тариф в сум/м³)

5. **ProductVolume** (Объёмы продукции):
   - Создание записей прогнозных объёмов выработки из прогнозных документов (с флагом `is_forecast = True`)
   - Связывание с Product и Period

6. **Расширение модели (опционально):**
   - **Tariff** (Тарифы) — если нет явной сущности, создать для хранения тарифов по энергоресурсам за периоды
   - **EquipmentCost** (Стоимость оборудования) — для хранения стоимости оборудования и работ из счёт-фактур и актов выполненных работ

**Связи между сущностями:**

После загрузки данных все сущности будут связаны через стандартные связи канонической модели:
- EnergyConsumption → EnergyResource, Period, EnergyAuditProject
- MeterReading → Meter, EnergyResource, Period
- Normative → EnergyResource, Product (опционально), Period (через valid_from/valid_to)
- ProductVolume → Product, Period, EnergyAuditProject

**Влияние на блокируемые показатели (N3.5):**

После загрузки данных из сканов следующие блокируемые показатели из N3.5 могут быть переведены из статуса "блокируется" в "частично обеспечен":

- **Полный энергобаланс по газу** (N3.5) → частично обеспечен (если загружены счёт-фактуры по газу)
- **Энергетический баланс по видам топлива** (N3.5) → частично обеспечен (если загружены счёт-фактуры по газу и расходу топлива)
- **Удельные показатели за период энергоаудита** (N3.5) → частично обеспечен (если загружены нормативные документы и данные по выработке)
- **Отклонения факт/норма** (N3.5) → частично обеспечен (если загружены нормативные документы)
- **Структура потребления по категориям** (N3.5) → частично обеспечен (если загружены документы по потерям)
- **Экономические показатели мероприятий** (N3.5) → частично обеспечен (если загружены счёт-фактуры и акты выполненных работ с тарифами и стоимостью)

**Примечание:** Полное закрытие блокируемых показателей возможно только при наличии всех необходимых данных (как из сканов, так и из таблиц Excel/CSV, полученных от заказчика). OCR-данные дополняют, но не всегда полностью заменяют структурированные данные.
