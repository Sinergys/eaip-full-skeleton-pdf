# План реализации ядра EAIP
## Energy Audit Information Platform — Core Implementation Plan

**Версия:** 1.0  
**Дата:** 2025-01-27  
**Статус:** В разработке (Шаг 1.2.e — разделы 2, 3, 4 и 5 заполнены)

---

## Введение

Этот документ описывает детализированный план реализации **ядра системы EAIP (Energy Audit Information Platform)** в рамках **Этапа 1** разработки. План опирается на техническое задание (`docs/EAIP_TZ.md`), архитектурное описание (`docs/EAIP_ARCHITECTURE.md`) и резюме с общим планом разработки (`docs/EAIP_TZ_SUMMARY_AND_PLAN.md`), а также учитывает результаты инвентаризации и анализа существующей кодовой базы (Шаг 1.1).

Документ не описывает полную реализацию всей системы EAIP, а фокусируется только на **ядре** — доменных моделях, справочниках, семи подсистемах логики энергопаспорта и их интеграции с существующими сервисами загрузки, валидации и генерации отчётов. План структурирован для поэтапной реализации с чёткими критериями готовности на каждом этапе.

## 2. Цели и границы плана реализации ядра EAIP

Этот раздел определяет, что конкретно входит в "ядро EAIP" для Этапа 1, а что вынесено за его пределы. План реализует базовую функциональность для работы с энергоресурсами, расчётами и формированием энергопаспортов согласно техническому заданию (раздел 9.3 ТЗ).

### 2.1. Цели реализации ядра

Цель реализации ядра EAIP на Этапе 1 — создать фундамент системы, который обеспечивает:

- **Каноническую модель данных** — единую внутреннюю модель, независимую от форматов представления (Excel, Word, PDF), как определено в ТЗ 1.3.1;
- **Расширяемые справочники** — возможность работы с любыми энергоресурсами через административный интерфейс без изменения кода (ТЗ 2.3);
- **Расчётную логику энергопаспорта** — реализацию всех семи подсистем логики энергопаспорта (ТЗ 4.6): Продукция, Нормы и фактический удельный расход, Энергопотребление по видам продукции, Структура энергопотребления предприятия, Энергетический баланс, Удельные показатели, Динамика удельных показателей;
- **Интеграцию с существующими сервисами** — базовую интеграцию ядра с уже реализованными сервисами загрузки (ingest), валидации (validate) и генерации отчётов (reports), но без жёсткой привязки к контейнеризации.

### 2.2. Границы и ограничения

#### 2.2.1. Что входит в ядро Этапа 1

В ядро Этапа 1 входят следующие компоненты:

1. **Каноническая доменная модель** — восемь основных сущностей из ТЗ 1.3.1: Предприятие (Enterprise), Проект энергоаудита (EnergyAuditProject), Периоды (Period), Виды продукции (Product), Энергоресурсы (EnergyResource), Площадки и здания (Building/Site), Узлы учёта (Meter), Нормативы (Normative), Расчётные показатели (CalculatedIndicators).

2. **Семь подсистем логики энергопаспорта** — полная реализация всех расчётных подсистем согласно ТЗ 4.6 с опорой на доменные модели и независимостью от конкретных форматов представления.

3. **Расширяемые справочники** — справочники энергоресурсов (EnergyResource), нормативов и единиц измерения с возможностью управления через административный интерфейс без изменения кода системы.

4. **Базовая интеграция с существующими сервисами** — интеграция доменных моделей с сервисами ingest (загрузка и парсинг), validate (валидация данных), reports (генерация отчётов) в режиме локального запуска без контейнеризации.

5. **Минимально необходимый веб-интерфейс** — базовые интерфейсы для создания/просмотра предприятий и проектов, управления справочниками, просмотра результатов расчётов.

#### 2.2.2. Что не входит в ядро Этапа 1

За пределами ядра Этапа 1 остаются следующие компоненты:

1. **Интеграции с внешними системами** — интеграция с внешними учётными системами предприятий, автоматический импорт нормативов из внешних источников, интеграция с внешними БД (ТЗ 9.1.1).

2. **Полноценный "боевой" веб-интерфейс** — расширенные интерфейсы для всех ролей пользователей, полный функционал управления проектами через UI, расширенные дашборды и аналитика. Минимально необходимый интерфейс входит, но полный UI — за пределами Этапа 1.

3. **Расширенная AI-подсистема** — базовые функции AI (анализ документов, обнаружение ошибок, генерация текстов) входят в ядро согласно ТЗ 4.8, но расширенные возможности и интеграции остаются за пределами Этапа 1.

4. **Docker / docker-compose / Kubernetes** — контейнеризация и оркестрация контейнеров не являются обязательным требованием для Этапа 1. Система должна запускаться локально из исходников (см. раздел 2.3).

5. **Мобильные приложения и многоязычность** — мобильные приложения и поддержка языков, кроме русского, не предусмотрены на первом этапе (ТЗ 9.1.1).

### 2.3. Запуск и окружение Этапа 1

**Целевой способ запуска сервисов на Этапе 1 — локальный запуск без контейнеризации.**

Сервисы должны запускаться напрямую из исходников через:
- Python и uvicorn для FastAPI-сервисов;
- poetry или pip для управления зависимостями;
- SQLite или локальная PostgreSQL для базы данных;
- локальные утилиты (Tesseract для OCR, и т.п.).

**Docker, docker-compose и Kubernetes рассматриваются как перспективное направление следующих этапов** и не входят в границы данного плана реализации ядра. Инфраструктурные решения, связанные с контейнеризацией, будут спроектированы и реализованы на последующих этапах разработки, когда ядро системы будет готово и протестировано в локальном режиме.

Это ограничение позволяет сосредоточиться на реализации бизнес-логики и доменных моделей без необходимости решения инфраструктурных задач контейнеризации на этапе формирования ядра системы.

## 3. Выбор структуры доменного слоя

Раздел рассматривает два варианта размещения доменных моделей ядра EAIP и обосновывает выбор целевой структуры для Этапа 1 с учётом текущей структуры репозитория и требований к переиспользованию кода между сервисами.

### 3.1. Вариант A: Общий доменный слой

**Описание:** Доменные модели размещаются в едином общем модуле, например `eaip_full_skeleton/core/domain/` или `eaip_full_skeleton/shared/domain/`, который переиспользуется всеми сервисами проекта.

**Плюсы:**
- Единая точка определения доменных сущностей — отсутствие дублирования моделей между сервисами;
- Чёткое разделение доменной логики от сервисной — соответствие принципам Domain-Driven Design;
- Простота сопровождения — изменения в доменных моделях вносятся в одном месте;
- Явная зависимость сервисов от домена — все сервисы явно используют один и тот же доменный слой;
- Соответствие архитектурному описанию — доменный слой выделен отдельно согласно `EAIP_ARCHITECTURE.md`.

**Минусы:**
- Требует реструктуризации текущего кода — доменные модели, которые сейчас находятся в `services/ingest/domain/`, нужно перенести в общий модуль;
- Необходимость настройки импортов во всех сервисах — каждый сервис должен корректно импортировать доменные модели из общего модуля;
- Риск "тяжёлых" зависимостей — если доменный модуль будет включать много зависимостей, это может усложнить структуру проекта.

**Риски:**
- **Архитектурный риск:** Может потребоваться существенная переработка существующего кода, что замедлит реализацию ядра;
- **Риск дублирования на переходном этапе:** При миграции может возникнуть временное дублирование моделей в старом и новом месте;
- **Риск нарушений изоляции сервисов:** Общий доменный слой может создать прямые зависимости между сервисами, если не спроектирован корректно.

### 3.2. Вариант B: Доменные модели в ingest-сервисе с последующим выносом

**Описание:** Доменные модели остаются в текущем расположении `eaip_full_skeleton/services/ingest/domain/`, но проектируются с учётом того, что они будут использоваться другими сервисами. Миграция в общий доменный слой планируется на более позднем этапе.

**Плюсы:**
- Минимальные изменения в текущей структуре — используется уже существующая организация кода;
- Быстрый старт реализации — не требуется предварительная реструктуризация;
- Постепенная эволюция архитектуры — можно выносить модели по мере необходимости;
- Меньше риска сломать существующий функционал — текущий код продолжает работать без изменений.

**Минусы:**
- Нарушение принципа переиспользования — другие сервисы вынуждены зависеть от ingest-сервиса только ради доменных моделей;
- Неочевидность архитектуры — не ясно, что доменные модели предназначены для общего использования;
- Риск дублирования — другие сервисы могут начать создавать собственные версии доменных моделей;
- Несоответствие архитектурному описанию — доменный слой не выделен отдельно, как описано в `EAIP_ARCHITECTURE.md`.

**Риски:**
- **Риск "застревания" в текущей структуре:** Модели могут остаться в ingest-сервисе, и их вынос станет техническим долгом;
- **Риск создания зависимостей от ingest-сервиса:** Другие сервисы (validate, reports, management) будут вынуждены импортировать из ingest, что создаёт нежелательные связи;
- **Риск дублирования кода:** Если вынос не будет выполнен вовремя, в разных сервисах могут появиться параллельные реализации доменных моделей.

### 3.3. Рекомендация для Этапа 1

**Рекомендуется использовать комбинированный подход с поэтапной миграцией:**

1. **Стартовая фаза (начало Этапа 1):** Использовать существующую структуру `eaip_full_skeleton/services/ingest/domain/` как основу для проектирования и реализации доменных моделей ядра. Это позволит быстро начать работу без реструктуризации кода.

2. **Целевая структура:** Спроектировать доменные модели с учётом их будущего выноса в общий доменный слой `eaip_full_skeleton/core/domain/`. Модели должны быть независимы от конкретного сервиса ingest и готовы к переиспользованию.

3. **План миграции:** После реализации базового набора доменных моделей (Enterprise, EnergyAuditProject, EnergyResource, Product и др.) выполнить их вынос в `eaip_full_skeleton/core/domain/` с обновлением импортов во всех затронутых сервисах. Миграция должна быть выполнена до начала интеграции расчётных подсистем, чтобы избежать накопления зависимостей от старой структуры.

**Обоснование рекомендации:**
- Учитывает текущую структуру репозитория и минимизирует риск поломки существующего функционала;
- Позволяет начать реализацию ядра без задержек на реструктуризацию;
- Сохраняет архитектурную цель (общий доменный слой) и планирует путь её достижения;
- Соответствует принципу постепенной эволюции архитектуры без резких изменений.

**Итоговый вывод:** Для реализации ядра Этапа 1 рекомендуется начать с использования существующей структуры `services/ingest/domain/` с явным планом по выносу доменных моделей в `core/domain/` в рамках того же Этапа 1 (после реализации базового набора моделей, но до начала интеграции расчётных подсистем). Это обеспечит баланс между скоростью реализации и архитектурной корректностью.

**Примечание:** Данная рекомендация касается только структуры доменного слоя и организации кода. Вопросы контейнеризации и инфраструктуры запуска (Docker, Kubernetes) не рассматриваются в этом разделе — они относятся к следующим этапам, как указано в разделе 2.3.

## 4. Каноническая доменная модель ядра (сущности первой итерации)

Раздел описывает доменные сущности первой итерации ядра EAIP, на которые опираются все расчёты энергопаспорта. Эти сущности формируют каноническую модель данных системы, независимую от форматов представления (Excel, Word, PDF), как определено в ТЗ 1.3.1. Описание каждой сущности включает назначение, ключевые атрибуты, связи с другими сущностями и роль в подсистемах расчётной логики.

### 4.1. Enterprise (Предприятие)

**Назначение:** Сущность представляет организацию, для которой проводится энергоаудит. Enterprise является корневым контейнером для всех данных, связанных с одним предприятием, включая проекты энергоаудита, площадки, здания и нормативные данные. Позволяет системе работать с несколькими предприятиями одновременно (мультитенантность).

**Основные атрибуты:**
- `id` — уникальный идентификатор (автогенерируемый)
- `name` — наименование предприятия
- `industry` — отрасль промышленности
- `activity_type` — тип деятельности предприятия
- `created_at` — дата создания записи
- `metadata` — дополнительные характеристики (опционально, JSON)

**Связи:**
- **1:М с EnergyAuditProject** — одно предприятие может иметь множество проектов энергоаудита (по годам, площадкам)
- **1:М с Site/Building** — предприятие содержит множество площадок и зданий
- Является корневой сущностью для всех остальных данных проекта

**Роль в подсистемах логики:** Enterprise не участвует напрямую в расчётах, но обеспечивает контекст и изоляцию данных. Все расчёты выполняются в контексте конкретного проекта (EnergyAuditProject), который связан с Enterprise.

---

### 4.2. EnergyAuditProject (Проект энергоаудита)

**Назначение:** Проект энергоаудита представляет контейнер для работы с энергоаудитом одного предприятия за конкретный временной период (год). Проект связывает все данные, необходимые для расчётов энергопаспорта: продукцию, энергопотребление, нормативы, результаты расчётов. Позволяет изолировать данные разных периодов и версионировать результаты расчётов.

**Основные атрибуты:**
- `id` — уникальный идентификатор
- `enterprise_id` — ссылка на Enterprise (обязательная связь)
- `year` — год энергоаудита
- `status` — статус проекта (draft, in_progress, validated, completed, archived)
- `created_at`, `updated_at` — даты создания и последнего обновления
- `version` — версия проекта (для версионирования при пересчётах)

**Связи:**
- **М:1 с Enterprise** — каждый проект принадлежит одному предприятию
- **1:М с Product** — проект содержит множество видов продукции
- **1:М с EnergyConsumption** — проект содержит данные по энергопотреблению
- **1:М с CalculatedIndicator** — проект содержит результаты расчётов

**Роль в подсистемах логики:** Все семь подсистем логики энергопаспорта работают в контексте конкретного проекта. Проект является основным контейнером для входных данных (продукция, энергопотребление) и выходных результатов расчётов (баланс, удельные показатели, динамика).

---

### 4.3. Period (Период)

**Назначение:** Период определяет временную структуру данных энергоаудита. Поддерживает иерархию периодов: год → квартал → месяц. Период используется для агрегации объёмов продукции, энергопотребления и результатов расчётов. Обеспечивает согласованность данных между уровнями (месяцы суммируются в кварталы, кварталы — в год).

**Основные атрибуты:**
- `id` — уникальный идентификатор
- `project_id` — ссылка на EnergyAuditProject
- `period_type` — тип периода (year, quarter, month)
- `year` — год периода
- `quarter` — квартал (1-4, если period_type = quarter)
- `month` — месяц (1-12, если period_type = month)

**Связи:**
- **М:1 с EnergyAuditProject** — периоды привязаны к проекту
- Используется в Product (объёмы по периодам), EnergyConsumption (потребление по периодам), CalculatedIndicator (результаты расчётов по периодам)

**Роль в подсистемах логики:** Критична для всех подсистем:
- **Подсистема "Продукция"** — объёмы выпуска по периодам
- **Подсистема "Энергопотребление по продукции"** — расчёт потребления по кварталам и годам
- **Подсистема "Структура потребления"** — распределение по периодам
- **Подсистема "Энергетический баланс"** — агрегация по периодам
- **Подсистема "Динамика"** — сравнение показателей между годами

---

### 4.4. Product (Виды продукции)

**Назначение:** Продукция представляет вид продукции предприятия, выпускаемой в рамках проекта энергоаудита. Продукция используется для расчёта энергопотребления на единицу продукции и удельных показателей. Поддерживает основную и побочную продукцию с различными единицами измерения объёмов производства.

**Основные атрибуты:**
- `id` — уникальный идентификатор
- `project_id` — ссылка на EnergyAuditProject (обязательная связь)
- `code` — код продукции
- `name` — наименование продукции
- `product_type` — тип (основная/побочная)
- `unit` — единица измерения объёма производства (т, кг, шт и т.п.)
- Объёмы выпуска хранятся через связь с Period или в структурированном виде (JSON: {year: {quarter: {month: volume}}})

**Связи:**
- **М:1 с EnergyAuditProject** — каждый вид продукции принадлежит одному проекту
- **1:М с Normative** — продукция может иметь нормативы по различным энергоресурсам
- Используется в расчётах EnergyConsumption (потребление по видам продукции)

**Роль в подсистемах логики:**
- **Подсистема "Продукция"** — хранение и агрегация объёмов выпуска по периодам
- **Подсистема "Нормы и фактический удельный расход"** — связь продукции с нормативами и фактическим потреблением
- **Подсистема "Энергопотребление по видам продукции"** — расчёт потребления на основе объёмов продукции и удельных расходов
- **Подсистема "Удельные показатели"** — расчёт удельных показателей на единицу продукции

---

### 4.5. EnergyResource (Энергоресурс)

**Назначение:** Энергоресурс представляет расширяемый справочник всех типов энергоресурсов, с которыми работает система (электроэнергия, газ, вода, топливо и др.). Сущность реализует требование ТЗ 2.3 о поддержке любых энергоресурсов без изменения кода через административный интерфейс. Энергоресурс содержит метаданные: единицы измерения, коэффициенты пересчёта в т.у.т., групповую классификацию.

**Основные атрибуты:**
- `id` — уникальный идентификатор
- `code` — краткий код латиницей (уникальный, например: ELEC, GAS, WATER, MAZUT, COAL)
- `name_ru` — полное наименование на русском языке
- `resource_group` — укрупнённая группа (electricity, gas, liquid_fuel, solid_fuel, water, heat, other)
- `unit_main` — каноническая единица учёта (кВт·ч, м³, т, Гкал)
- `k_tut` — коэффициент пересчёта в тонны условного топлива (т.у.т.)
- `is_active` — флаг активности (возможность деактивации без удаления)
- `normative_source` — ссылка на нормативный источник (НД, методика)
- `subtype` — подтип ресурса (опционально, для иерархии, например: electricity → active/reactive/total)
- Допустимые единицы измерения через связанную структуру (EnergyResourceUnit) с коэффициентами приведения к `unit_main`

**Связи:**
- **1:М с EnergyConsumption** — энергоресурс используется в записях потребления
- **1:М с Normative** — для энергоресурса определены нормативы
- **1:М с CalculatedIndicator** — результаты расчётов привязаны к энергоресурсу

**Роль в подсистемах логики:** Критична для всех подсистем:
- **Подсистема "Нормы и фактический удельный расход"** — нормативы и факт привязаны к конкретным ресурсам
- **Подсистема "Энергопотребление по видам продукции"** — потребление рассчитывается по каждому ресурсу отдельно
- **Подсистема "Структура потребления"** — распределение по категориям выполняется по каждому ресурсу
- **Подсистема "Энергетический баланс"** — агрегация всех ресурсов с пересчётом в т.у.т. через коэффициенты
- **Подсистема "Удельные показатели"** — расчёт удельных показателей по ресурсам
- **Подсистема "Динамика"** — сравнение динамики по ресурсам

---

### 4.6. Site/Building (Площадка/Здание)

**Назначение:** Площадка или здание представляет физическую структуру предприятия (производственное здание, офис, склад и т.п.). Используется для расчёта удельных показателей на единицу площади (кВт·ч/м², м³/м²). Площади суммируются для получения общей площади предприятия, необходимой для расчётов по подсистеме "Удельные показатели".

**Основные атрибуты:**
- `id` — уникальный идентификатор
- `enterprise_id` — ссылка на Enterprise
- `name` — наименование площадки/здания
- `area_m2` — площадь в м²
- `facility_type` — тип здания (производственное, административное, склад и т.п.)
- `purpose` — назначение (опционально)

**Связи:**
- **М:1 с Enterprise** — площадки принадлежат предприятию
- **1:М с Meter** — площадки могут содержать узлы учёта
- Используется в расчётах удельных показателей на площадь

**Роль в подсистемах логики:**
- **Подсистема "Удельные показатели"** — расчёт удельных показателей на м² (кВт·ч/м², м³/м² и т.п.)
- **Подсистема "Нормы и фактический удельный расход"** — нормативы по площади (Норматив с типом per_area)

---

### 4.7. Meter (Узел учёта)

**Назначение:** Узел учёта представляет точку измерения энергоресурса (счётчик, узел учёта). Метры связаны с конкретными энергоресурсами и площадками, хранят временные ряды показаний. Используются для получения фактического энергопотребления, которое затем агрегируется по периодам и распределяется по категориям использования.

**Основные атрибуты:**
- `id` — уникальный идентификатор
- `project_id` — ссылка на EnergyAuditProject
- `resource_id` — ссылка на EnergyResource (какой ресурс измеряет счётчик)
- `site_id` — ссылка на Site/Building (где установлен счётчик, опционально)
- `name` — наименование узла учёта
- `meter_readings` — массив временных рядов показаний (JSON: структура по периодам)
- `meter_number` — номер счётчика (опционально)

**Связи:**
- **М:1 с EnergyAuditProject** — узлы учёта привязаны к проекту
- **М:1 с EnergyResource** — узел измеряет конкретный энергоресурс
- **М:1 с Site/Building** — узел может быть привязан к площадке (опционально)
- Используется в EnergyConsumption для получения фактических данных потребления

**Роль в подсистемах логики:**
- **Подсистема "Структура энергопотребления"** — показания узлов учёта используются для определения фактического потребления и его распределения по категориям (производство, потери, хоз-быт)
- **Подсистема "Энергопотребление по видам продукции"** — показания могут использоваться для валидации расчётных значений потребления

---

### 4.8. Normative (Норматив)

**Назначение:** Норматив представляет нормативные значения удельного потребления энергоресурсов. Нормативы могут быть привязаны к продукции (кВт·ч/т, м³/т) или к площади (кВт·ч/м², м³/м²). Нормативы поддерживают версионирование и привязку к периоду действия, что позволяет отслеживать изменения нормативной базы во времени. Источники нормативов (НД, методики) фиксируются для обеспечения прозрачности расчётов.

**Основные атрибуты:**
- `id` — уникальный идентификатор
- `resource_id` — ссылка на EnergyResource (обязательная связь)
- `product_id` — ссылка на Product (опционально, если норматив по продукции)
- `normative_type` — тип норматива (per_product, per_area)
- `value` — нормативное значение
- `unit` — единица измерения (кВт·ч/т, м³/м² и т.п.)
- `source` — источник норматива (НД, методика, например: ПКМ-690, СНиП, ГОСТ)
- `valid_from` — дата начала действия норматива
- `valid_to` — дата окончания действия (опционально)
- `version` — версия норматива

**Связи:**
- **М:1 с EnergyResource** — норматив привязан к энергоресурсу
- **М:1 с Product** — норматив по продукции привязан к виду продукции (опционально)
- Используется в расчётах отклонений фактических показателей от нормативных

**Роль в подсистемах логики:**
- **Подсистема "Нормы и фактический удельный расход"** — нормативные значения сравниваются с фактическими для расчёта отклонений
- **Подсистема "Удельные показатели"** — нормативы по площади используются для сравнения фактических удельных показателей на м²
- **Подсистема "Динамика"** — изменения нормативов могут учитываться при анализе динамики

---

### 4.9. CalculatedIndicator и связанные сущности (Расчётные показатели)

**Назначение:** Группа сущностей для представления результатов расчётов семи подсистем логики энергопаспорта. Включает потребление по видам продукции и ресурсам, структуру потребления (производство, потери, хоз-быт), энергетический баланс, удельные показатели, динамику и отклонения "факт/норма". Эти сущности хранят вычисленные значения, которые используются для формирования отчётов и энергопаспорта.

**Основные сущности группы:**

#### 4.9.1. EnergyConsumption (Энергопотребление)

**Назначение:** Фактическое потребление энергоресурсов по периодам. Хранит потребление в канонических единицах и в т.у.т., структуру потребления по категориям (производство, потери, хоз-быт), связь с узлами учёта.

**Основные атрибуты:**
- `id` — уникальный идентификатор
- `project_id` — ссылка на EnergyAuditProject
- `resource_id` — ссылка на EnergyResource
- `period_type`, `period_value`, `year` — привязка к периоду
- `consumption_main_unit` — потребление в канонической единице ресурса
- `consumption_tut` — потребление в т.у.т.
- `by_usage` — структура потребления по назначению (JSON: {production, losses, household, own_needs})
- `cost` — стоимость потребления (опционально)

**Роль в подсистемах:**
- **Подсистема "Энергопотребление по видам продукции"** — хранит расчётное потребление на основе объёмов продукции
- **Подсистема "Структура потребления"** — хранит распределение по категориям использования
- **Подсистема "Энергетический баланс"** — используется для формирования строк баланса

#### 4.9.2. EnergyBalanceRow (Строка энергобаланса)

**Назначение:** Представляет одну строку энергетического баланса предприятия (например, "1. Продукция (услуга)", "2. Технологические потери" и т.п.). Агрегирует потребление по всем ресурсам и пересчитывает в т.у.т.

**Основные атрибуты:**
- `id` — уникальный идентификатор
- `project_id` — ссылка на EnergyAuditProject
- `balance_row_type` — тип строки баланса (production, losses, household, own_needs)
- `period_type`, `period_value`, `year` — привязка к периоду
- `balance_data` — данные баланса по ресурсам (JSON: {resource_id: {consumption_main_unit, consumption_tut}})
- `total_tut` — общее потребление в т.у.т. по строке баланса

**Роль в подсистемах:**
- **Подсистема "Энергетический баланс"** — представляет результат агрегации и пересчёта всех ресурсов в т.у.т.

#### 4.9.3. SpecificIndicator (Удельный показатель)

**Назначение:** Хранит удельные показатели энергопотребления (на единицу продукции или на м²), фактическое и нормативное значения, отклонения.

**Основные атрибуты:**
- `id` — уникальный идентификатор
- `project_id` — ссылка на EnergyAuditProject
- `resource_id` — ссылка на EnergyResource
- `product_id` — ссылка на Product (если показатель на продукцию, опционально)
- `indicator_type` — тип показателя (per_product, per_area)
- `year` — год
- `actual_value` — фактическое значение
- `normative_value` — нормативное значение
- `deviation_abs` — абсолютное отклонение (факт - норма)
- `deviation_percent` — относительное отклонение (%)

**Роль в подсистемах:**
- **Подсистема "Удельные показатели"** — хранит результаты расчёта удельных показателей и их сравнения с нормативами

#### 4.9.4. Dynamics (Динамика показателей)

**Назначение:** Хранит динамику удельных показателей по годам для нескольких проектов энергоаудита, тренды и изменения.

**Основные атрибуты:**
- `id` — уникальный идентификатор
- `project_ids` — ссылки на несколько проектов разных лет (массив ID)
- `resource_id` — ссылка на EnergyResource
- `indicator_type` — тип показателя
- `years_data` — данные по годам (JSON: {year: value})
- `trend` — тренд (growth, decline, stable)
- `changes` — изменения между годами (JSON: {year: {abs_change, percent_change}})

**Роль в подсистемах:**
- **Подсистема "Динамика удельных показателей"** — хранит результаты анализа динамики по годам

**Связи всей группы CalculatedIndicator:**
- Все сущности группы связаны с EnergyAuditProject (М:1)
- Связаны с EnergyResource через resource_id
- Используются для формирования отчётов и энергопаспорта

**Роль в подсистемах логики:** Группа CalculatedIndicator хранит результаты расчётов всех семи подсистем логики энергопаспорта. Эти сущности формируются в процессе выполнения расчётов и используются как источник данных для генерации отчётов и заполнения шаблонов энергопаспорта.

## 5. Сопоставление доменных моделей с текущей структурой БД

Раздел анализирует текущую структуру базы данных в `eaip_full_skeleton/services/ingest/database.py` (SQLite) и сопоставляет её с требованиями доменной модели ядра EAIP, описанной в разделе 4. На основе анализа определяются необходимые изменения в БД для поддержки всех доменных сущностей и семи подсистем логики энергопаспорта.

### 5.1. Общий обзор текущей БД

Текущая структура БД в `eaip_full_skeleton/services/ingest/database.py` ориентирована на функционал загрузки и парсинга файлов (ingest-сервис) и содержит следующие основные группы таблиц:

**Технические таблицы для ingest:**
- `enterprises` — базовая таблица предприятий (3 поля: id, name, created_at)
- `uploads` — метаданные загруженных файлов (batch_id, enterprise_id, filename, file_type, status, parsing_summary)
- `parsed_data` — сырые распарсенные данные в формате JSON (raw_json, editable_text)
- `uploads_storage` — технические метаданные файлов (file_hash, file_mtime)

**Таблицы для нормативных документов:**
- `normative_documents` — записи о загруженных нормативных документах (PDF, Word и т.п.)
- `normative_rules` — правила/нормативы, извлечённые из документов
- `normative_references` — связи правил с полями энергопаспорта

**Ограничения текущей схемы:**
- Отсутствует явная таблица проектов энергоаудита (EnergyAuditProject) — нет концепции проектов по годам
- Нет справочника энергоресурсов (EnergyResource) как расширяемой таблицы
- Нет таблиц для продукции (Product), площадок/зданий (Site/Building), узлов учёта (Meter)
- Нет таблиц для результатов расчётов (EnergyConsumption, EnergyBalanceRow, SpecificIndicator, Dynamics)
- Данные хранятся в JSON-формате (parsed_data.raw_json), что не позволяет эффективно использовать их в расчётах
- Таблица `enterprises` содержит только базовые поля, не хватает industry, activity_type и других атрибутов
- Таблицы для нормативных документов имеют другую логику (связь с документами, AI-извлечение), не соответствуют доменной сущности Normative

### 5.2. Таблица соответствия: доменные сущности ↔ таблицы БД

#### 5.2.1. Enterprise (Предприятие)

**Текущее состояние в БД:**
- Соответствует таблице `enterprises` с полями: `id`, `name`, `created_at`
- Таблица используется как корневая для связывания загруженных файлов (`uploads.enterprise_id`)

**Проблемы/ограничения:**
- Отсутствуют поля: `industry` (отрасль), `activity_type` (тип деятельности), `metadata` (дополнительные характеристики)
- Таблица не имеет явной связи с проектами энергоаудита (нет таблицы проектов)

**Что нужно сделать:**
- Дополнить таблицу `enterprises` полями: `industry` (TEXT), `activity_type` (TEXT), `metadata` (JSON/TEXT для хранения дополнительных данных)
- Оставить существующую структуру как основу, добавив недостающие поля через миграцию

---

#### 5.2.2. EnergyAuditProject (Проект энергоаудита)

**Текущее состояние в БД:**
- Таблица отсутствует. Концепция проектов не реализована.
- Связь с предприятием есть только на уровне загруженных файлов (`uploads.enterprise_id`)

**Проблемы/ограничения:**
- Нет способа группировать данные по проектам (годам, периодам)
- Нет версионирования проектов
- Нет статусов проектов (draft, in_progress, validated, completed, archived)
- Все расчёты привязаны к проектам — без таблицы проектов невозможно реализовать подсистемы логики энергопаспорта

**Что нужно сделать:**
- **Создать новую таблицу `energy_audit_projects`** с полями:
  - `id` (PRIMARY KEY)
  - `enterprise_id` (FOREIGN KEY → enterprises.id)
  - `year` (INTEGER, год энергоаудита)
  - `status` (TEXT: draft, in_progress, validated, completed, archived)
