## 1. Обзор архитектуры

### 1.1. Принципы архитектуры

EAIP построена на следующих ключевых принципах:

1. **Каноническая модель данных** — единая внутренняя модель данных, независимая от форматов представления (Excel, Word, PDF)
2. **Расширяемость без изменения кода** — справочники, нормативы, шаблоны настраиваются через UI, а не через код
3. **Domain-Driven Design** — разделение на слои: domain, application, infrastructure, presentation
4. **Микросервисная архитектура** — разделение функциональности на независимые сервисы
5. **Мультитенантность** — поддержка работы с несколькими предприятиями и проектами одновременно

### 1.2. Архитектурные слои

```
┌─────────────────────────────────────────────────────────┐
│                  Presentation Layer                      │
│  (Web UI, REST API, файловые форматы вывода)            │
└───────────────────┬─────────────────────────────────────┘
                    │
┌───────────────────▼─────────────────────────────────────┐
│               Application Layer                          │
│  (Use Cases, Workflow, Business Logic Orchestration)    │
└───────────────────┬─────────────────────────────────────┘
                    │
┌───────────────────▼─────────────────────────────────────┐
│                 Domain Layer                             │
│  (Entities, Value Objects, Domain Services, Rules)      │
└───────────────────┬─────────────────────────────────────┘
                    │
┌───────────────────▼─────────────────────────────────────┐
│              Infrastructure Layer                        │
│  (Database, File Storage, External APIs, OCR, AI)       │
└─────────────────────────────────────────────────────────┘
```

## 2. Доменная область

### 2.1. Ключевые сущности (Domain Entities)

#### 2.1.1. Энергоресурс (EnergyResource)

**Описание:** Расширяемый справочник всех типов энергоресурсов, с которыми работает система.

**Атрибуты:**
- `id` — уникальный идентификатор
- `code` — краткий код латиницей (ELEC, GAS, WATER, MAZUT, COAL и т.п.)
- `name_ru` — полное наименование на русском языке
- `resource_group` — укрупнённая группа (electricity, gas, liquid_fuel, solid_fuel, water, heat, other)
- `unit_main` — каноническая единица учёта (кВт·ч, м³, т, Гкал)
- `allowed_units` — допустимые единицы ввода с коэффициентами пересчёта
- `k_tut` — коэффициент пересчёта в т.у.т.
- `is_active` — флаг активности
- `normative_source` — ссылка на нормативный документ
- `subtype` — подтип ресурса (опционально, для иерархии)

**Особенности:**
- Расширяемость через административный интерфейс без изменения кода
- Иерархия ресурсов через `resource_group` и `subtype`
- Поддержка различных единиц измерения через коэффициенты пересчёта

#### 2.1.2. Предприятие (Enterprise)

**Описание:** Организация, для которой проводится энергоаудит.

**Атрибуты:**
- `id` — уникальный идентификатор
- `name` — наименование предприятия
- `industry` — отрасль (✅ реализовано 2025-11-30)
- `enterprise_type` — тип предприятия (✅ реализовано 2025-11-30, соответствует `activity_type`)
- `product_type` — тип продукции (✅ реализовано 2025-11-30)
- `created_at` — дата создания

**Функциональность:**
- ✅ Автоматическое определение типа предприятия на основе анализа загруженных файлов
- ✅ Классификатор учитывает контекст файлов (про само предприятие vs про потребителей)
- ✅ Приоритет названию предприятия при определении отрасли

**Связи:**
- Имеет множество проектов энергоаудита
- Имеет множество площадок/зданий
- Использует множество видов продукции

#### 2.1.3. Проект энергоаудита (EnergyAuditProject)

**Описание:** Контейнер для работы с энергоаудитом одного предприятия за конкретный период.

**Атрибуты:**
- `id` — уникальный идентификатор
- `enterprise_id` — ссылка на предприятие
- `year` — год энергоаудита
- `period_type` — тип периода (year, quarter, month)
- `status` — статус проекта (draft, in_progress, validated, completed, archived)
- `created_at` — дата создания
- `updated_at` — дата последнего обновления
- `version` — версия проекта (для версионирования при пересчётах)

**Связи:**
- Ссылается на одно предприятие
- Содержит данные по продукции
- Содержит данные по энергопотреблению
- Содержит результаты расчётов

#### 2.1.4. Продукция (Product)

**Описание:** Вид продукции предприятия, выпускаемой в рамках проекта.

**Атрибуты:**
- `id` — уникальный идентификатор
- `project_id` — ссылка на проект
- `code` — код продукции
- `name` — наименование
- `product_type` — тип (основная/побочная)
- `unit` — единица измерения объёма производства
- `volumes` — объёмы выпуска по периодам (JSON: {year: {quarter: {month: volume}}})
- `normatives` — нормативные удельные расходы по ресурсам (JSON)

**Связи:**
- Принадлежит одному проекту
- Имеет нормативы по различным энергоресурсам
- Используется в расчётах энергопотребления

#### 2.1.5. Потребление энергоресурсов (EnergyConsumption)

**Описание:** Фактическое потребление энергоресурсов по периодам.

**Атрибуты:**
- `id` — уникальный идентификатор
- `project_id` — ссылка на проект
- `resource_id` — ссылка на энергоресурс
- `period_type` — тип периода (month, quarter, year)
- `period_value` — значение периода (месяц 1-12, квартал 1-4, год)
- `year` — год
- `consumption_main_unit` — потребление в канонической единице
- `consumption_tut` — потребление в т.у.т.
- `by_usage` — структура потребления по назначению (JSON: {production, losses, household, own_needs})
- `meter_readings` — показания узлов учёта (JSON)
- `cost` — стоимость потребления

**Связи:**
- Принадлежит одному проекту
- Ссылается на один энергоресурс
- Может быть привязано к узлам учёта

#### 2.1.6. Энергобаланс (EnergyBalance)

**Описание:** Сводный энергобаланс предприятия по всем ресурсам и назначениям.

**Атрибуты:**
- `id` — уникальный идентификатор
- `project_id` — ссылка на проект
- `period_type` — тип периода
- `period_value` — значение периода
- `year` — год
- `balance_data` — данные баланса (JSON: структура по ресурсам и назначениям)
- `total_tut` — общее потребление в т.у.т.

**Особенности:**
- Агрегирует данные из подсистемы «Энергопотребление по продукции» и «Структура потребления»
- Выполняет пересчёт всех ресурсов в т.у.т.

#### 2.1.7. Удельные показатели (SpecificIndicators)

**Описание:** Удельные показатели энергопотребления.

**Атрибуты:**
- `id` — уникальный идентификатор
- `project_id` — ссылка на проект
- `indicator_type` — тип показателя (per_product, per_area)
- `resource_id` — ссылка на энергоресурс
- `year` — год
- `actual_value` — фактическое значение
- `normative_value` — нормативное значение
- `deviation_abs` — абсолютное отклонение
- `deviation_percent` — относительное отклонение (%)

**Связи:**
- Принадлежит одному проекту
- Ссылается на энергоресурс и/или продукцию

#### 2.1.8. Динамика показателей (Dynamics)

**Описание:** Динамика удельных показателей по годам.

**Атрибуты:**
- `id` — уникальный идентификатор
- `project_id` — ссылка на проект (может ссылаться на несколько проектов разных лет)
- `indicator_type` — тип показателя
- `resource_id` — ссылка на энергоресурс
- `years_data` — данные по годам (JSON: {year: value})
- `trend` — тренд (growth, decline, stable)
- `changes` — изменения (JSON: {year: {abs_change, percent_change}})

### 2.2. Справочные сущности

#### 2.2.1. Норматив (Normative)

**Описание:** Нормативные значения удельного потребления.

**Атрибуты:**
- `id` — уникальный идентификатор
- `resource_id` — ссылка на энергоресурс
- `product_id` — ссылка на продукцию (опционально)
- `normative_type` — тип норматива (per_product, per_area)
- `value` — нормативное значение
- `unit` — единица измерения
- `source` — источник норматива (НД, методика)
- `valid_from` — дата начала действия
- `valid_to` — дата окончания действия (опционально)
- `version` — версия норматива

**Особенности:**
- Версионирование для отслеживания изменений нормативов
- Привязка к периоду действия

#### 2.2.2. Площадка/здание (Facility)

**Описание:** Площадка или здание предприятия.

**Атрибуты:**
- `id` — уникальный идентификатор
- `enterprise_id` — ссылка на предприятие
- `name` — наименование
- `area_m2` — площадь в м²
- `facility_type` — тип здания
- `purpose` — назначение

### 2.3. Ключевые потоки данных

#### 2.3.1. Поток загрузки и обработки данных

```
Файлы предприятия
    ↓
[Загрузка файлов] → ingest service
    ↓
[Классификация файлов] → автоматическое определение типа документа
    ↓
[OCR/Парсинг] → извлечение структурированных данных
    ↓
[Структурирование] → преобразование в каноническую модель
    ↓
[Валидация] → проверка согласованности
    ↓
[Верификация] → ручная проверка с подсказками ИИ
    ↓
[Сохранение в БД] → каноническая модель данных
```

#### 2.3.2. Поток расчётов

```
Каноническая модель данных
    ↓
[Подсистема "Продукция"] → агрегация объёмов по периодам
    ↓
[Подсистема "Нормы и факт"] → расчёт удельных расходов
    ↓
[Подсистема "Энергопотребление по продукции"] → потребление по видам продукции
    ↓
[Подсистема "Структура потребления"] → распределение по категориям
    ↓
[Подсистема "Энергетический баланс"] → агрегация и пересчёт в т.у.т.
    ↓
[Подсистема "Удельные показатели"] → расчёт удельных показателей
    ↓
[Подсистема "Динамика"] → анализ динамики по годам
    ↓
Результаты расчётов
```

#### 2.3.3. Поток формирования отчётов

```
Результаты расчётов
    ↓
[Аналитические таблицы] → промежуточные таблицы и диаграммы
    ↓
[Текстовые разделы] → генерация текстов через ИИ
    ↓
[Формирование отчёта] → Word-отчёт
    ↓
[Заполнение энергопаспорта] → Excel-шаблон (ПКМ-690)
    ↓
[Экспорт] → готовые документы
```

## 3. Целевая архитектура системы

### 3.1. Микросервисная архитектура

EAIP построена как набор независимых микросервисов, взаимодействующих через REST API и общую базу данных.

#### 3.1.1. Сервисы системы

**1. Gateway-Auth Service (Порт: 8000)**
- **Назначение:** API Gateway и аутентификация
- **Функции:**
  - Маршрутизация запросов к сервисам
  - Аутентификация пользователей (JWT)
  - Авторизация и проверка прав доступа (RBAC)
  - Управление сессиями

**2. Ingest Service (Порт: 8001)**
- **Назначение:** Загрузка и обработка файлов
- **Функции:**
  - Загрузка файлов через веб-интерфейс
  - Классификация файлов по типу документа
  - Парсинг Excel, Word, PDF
  - OCR для сканированных документов
  - Структурирование данных в каноническую модель
  - Интеграция с AI для улучшения распознавания

**3. Validate Service (Порт: 8002)**
- **Назначение:** Проверка согласованности данных
- **Функции:**
  - Автоматические проверки согласованности
  - Выявление аномалий
  - Формирование списков ошибок и предупреждений
  - Интеграция с AI для дополнительных проверок

**4. Reports Service (Порт: 8003)**
- **Назначение:** Формирование отчётов и энергопаспортов
- **Функции:**
  - Генерация аналитических таблиц и диаграмм
  - Формирование Word-отчётов
  - Заполнение Excel-энергопаспортов (ПКМ-690)
  - Экспорт в PDF
  - Генерация текстов разделов через AI

**5. Recommend Service (Порт: 8004)**
- **Назначение:** AI-рекомендации и анализ
- **Функции:**
  - Анализ документов и данных
  - Обнаружение ошибок и аномалий
  - Генерация предложений по корректировкам
  - Генерация мероприятий по энергоэффективности
  - Контекстная AI-панель для проектов

**6. Management Service (Порт: 8005)**
- **Назначение:** Управление проектами и администрирование
- **Функции:**
  - Управление проектами энергоаудита
  - Управление справочниками (энергоресурсы, продукция, нормативы)
  - Управление пользователями и ролями
  - Генерация пакета документов для сбора данных
  - Управление архивом проектов

**7. Analytics Service (Порт: 8006)**
- **Назначение:** Аналитика и прогнозирование
- **Функции:**
  - Анализ динамики показателей
  - Прогнозирование энергопотребления
  - Сравнительная аналитика

### 3.2. Слои каждого сервиса

Каждый микросервис организован по слоям:

```
Service/
├── domain/              # Domain Layer
│   ├── entities/       # Доменные сущности
│   ├── value_objects/  # Value Objects
│   └── services/       # Domain Services
├── application/        # Application Layer
│   ├── use_cases/     # Use Cases
│   ├── dto/           # Data Transfer Objects
│   └── interfaces/    # Интерфейсы
├── infrastructure/     # Infrastructure Layer
│   ├── database/      # Репозитории БД
│   ├── external/      # Внешние API (AI, OCR)
│   └── storage/       # Файловое хранилище
└── presentation/       # Presentation Layer
    ├── api/           # REST API endpoints
    └── web/           # Веб-интерфейс (если есть)
```

### 3.3. Инфраструктура

#### 3.3.1. База данных

**PostgreSQL** — основная СУБД для структурированных данных:
- Справочники
- Проекты и данные предприятий
- Пользователи и права доступа
- История изменений
- Результаты расчётов

**Схема БД:**
- Разделение по схемам/префиксам для каждого сервиса (при необходимости)
- Единая схема `eaip_*` для общих сущностей (enterprises, projects, energy_resources)

#### 3.3.2. Файловое хранилище

**MinIO или S3-совместимое хранилище:**
- Хранение исходных файлов от предприятий
- Хранение сгенерированных отчётов
- Организация по структуре: `projects/{project_id}/documents/{type}/`
- Версионирование файлов

#### 3.3.3. Кэширование

**Redis** (опционально):
- Кэширование справочников
- Кэширование результатов расчётов
- Сессии пользователей
- Очереди задач (для асинхронной обработки)

#### 3.3.4. Внешние интеграции

**AI-провайдеры:**
- OpenAI (GPT-4, GPT-3.5)
- DeepSeek (локальные/облачные модели)
- Плагинная архитектура для добавления новых провайдеров

**OCR:**
- Tesseract (локальный)
- Коммерческие решения (при необходимости)
- AI Vision API для улучшения распознавания

## 4. Ключевые интерфейсы и границы

### 4.1. Интерфейс справочника энергоресурсов

**Описание:** Абстракция для работы с расширяемым справочником энергоресурсов.

**Ключевые методы:**
```python
class EnergyResourceRepository:
    def get_by_code(code: str) -> EnergyResource
    def get_active_resources() -> List[EnergyResource]
    def create(resource: EnergyResource) -> EnergyResource
    def update(resource: EnergyResource) -> EnergyResource
    def get_by_group(group: str) -> List[EnergyResource]
    def convert_to_main_unit(resource_id: int, value: float, unit: str) -> float
    def convert_to_tut(resource_id: int, value: float) -> float
```

**Реализация:**
- Infrastructure: `PostgreSQLEnergyResourceRepository`
- Валидация при создании/обновлении
- Кэширование справочника

### 4.2. Интерфейс расчётного движка

**Описание:** Абстракция для выполнения расчётов энергопаспорта.

**Ключевые методы:**
```python
class CalculationEngine:
    def calculate_product_volumes(project_id: int) -> Dict
    def calculate_specific_consumption(project_id: int) -> Dict
    def calculate_energy_consumption_by_products(project_id: int) -> Dict
    def calculate_consumption_structure(project_id: int) -> Dict
    def calculate_energy_balance(project_id: int) -> Dict
    def calculate_specific_indicators(project_id: int) -> Dict
    def calculate_dynamics(project_ids: List[int]) -> Dict
    def recalculate_all(project_id: int) -> Dict
```

**Особенности:**
- Зависимости между расчётами через dependency graph
- Автоматический пересчёт зависимых показателей
- Кэширование результатов

### 4.3. Интерфейс импорта/экспорта шаблонов

**Описание:** Абстракция для работы с различными шаблонами отчётов.

**Ключевые методы:**
```python
class TemplateAdapter:
    def import_from_template(template_path: str, project_id: int) -> Dict
    def export_to_template(project_id: int, template_path: str) -> str
    def validate_template_structure(template_path: str) -> bool
    def get_template_fields(template_path: str) -> Dict
```

**Реализации:**
- `PKM690ExcelAdapter` — импорт/экспорт шаблона ПКМ-690
- Возможность добавления новых адаптеров для других шаблонов

### 4.4. Интерфейс AI-подсистемы

**Описание:** Единый интерфейс для работы с различными AI-провайдерами.

**Ключевые методы:**
```python
class AIService:
    def analyze_document(document_path: str, context: Dict) -> Dict
    def detect_anomalies(data: Dict, context: Dict) -> List[Dict]
    def generate_suggestions(issue: Dict, context: Dict) -> Dict
    def generate_report_section(section_type: str, data: Dict) -> str
    def generate_energy_efficiency_measures(data: Dict) -> List[Dict]
```

**Реализации:**
- `OpenAIService` — интеграция с OpenAI
- `DeepSeekService` — интеграция с DeepSeek
- Возможность переключения провайдеров без изменения кода

## 5. Места, где особенно важна расширяемость

### 5.1. Расширяемость энергоресурсов

**Принцип:** Новые типы энергоресурсов добавляются через справочник, а не через код.

**Механизм:**
1. Администратор добавляет новый ресурс через UI
2. Система проверяет корректность данных (код, единицы, коэффициенты)
3. Новый ресурс становится доступным во всех модулях системы без изменения кода

**Важные интерфейсы:**
- Расчётный движок работает с абстракцией `EnergyResource`, а не с конкретными типами
- Импорт/экспорт адаптируется к новым ресурсам автоматически

### 5.2. Расширяемость нормативов

**Принцип:** Нормативы хранятся в справочниках и версионируются.

**Механизм:**
1. Нормативы привязаны к периодам действия
2. При обновлении нормативов создаётся новая версия
3. Проекты могут ссылаться на конкретную версию нормативов
4. Возможен пересчёт проектов с новыми нормативами

### 5.3. Расширяемость отчётных шаблонов

**Принцип:** Поддержка различных шаблонов через плагинную систему.

**Механизм:**
1. Каждый шаблон имеет свой адаптер (`TemplateAdapter`)
2. Адаптер знает структуру шаблона и способ заполнения
3. Новые шаблоны добавляются без изменения ядра системы

**Примеры:**
- Шаблон ПКМ-690 (текущая версия)
- Обновлённый шаблон ПКМ-690 (будущие версии)
- Специализированные шаблоны для различных отраслей

### 5.4. Расширяемость AI-подсистемы

**Принцип:** Единый интерфейс для различных AI-провайдеров.

**Механизм:**
1. Абстрактный интерфейс `AIService`
2. Конкретные реализации для каждого провайдера
3. Переключение провайдеров через конфигурацию

**Возможности:**
- Использование локальных моделей (DeepSeek, Ollama)
- Использование облачных моделей (OpenAI, Anthropic)
- Комбинирование различных моделей для разных задач

### 5.5. Расширяемость правил валидации

**Принцип:** Правила валидации конфигурируемы, а не зашиты в код.

**Механизм:**
1. Правила валидации хранятся в конфигурации или БД
2. Возможность добавления новых правил через административный интерфейс
3. Пороги и допуски настраиваемы

## 6. Технические решения

### 6.1. Технологический стек

**Backend:**
- Python 3.11+
- FastAPI — фреймворк для REST API
- SQLAlchemy — ORM для работы с БД
- Pydantic — валидация данных

**Frontend:**
- HTML/CSS/JavaScript
- Современные браузеры (Chrome, Firefox, Edge, Safari)

**База данных:**
- PostgreSQL 14+ — основная СУБД
- SQLite — для локальной разработки (ingest service)

**Файловое хранилище:**
- MinIO — S3-совместимое хранилище

**AI/OCR:**
- OpenAI API
- DeepSeek API
- Tesseract OCR
- Poppler (для работы с PDF)

**Инфраструктура:**
- Docker — контейнеризация
- docker-compose — оркестрация сервисов

### 6.2. Паттерны проектирования

**Repository Pattern** — абстракция доступа к данным
**Service Layer Pattern** — бизнес-логика в сервисах
**Adapter Pattern** — адаптеры для различных шаблонов и AI-провайдеров
**Factory Pattern** — создание объектов (AI-клиенты, парсеры)
**Strategy Pattern** — различные стратегии расчётов и валидаций

### 6.3. Обработка зависимостей расчётов

**Dependency Graph:**
- Определение порядка выполнения расчётов
- Автоматический пересчёт зависимых показателей при изменении исходных данных
- Оптимизация производительности (параллельные расчёты для независимых данных)

**Пример зависимостей:**
```
Энергобаланс
    ↓ зависит от
[Энергопотребление по продукции] + [Структура потребления]
    ↓ зависит от
[Нормы и факт] + [Продукция]
    ↓ зависит от
[Исходные данные]
```

## 7. Безопасность и изоляция данных

### 7.1. Мультитенантность

**Уровень изоляции:**
- Изоляция данных на уровне предприятий
- Проекты привязаны к предприятиям
- Пользователи имеют доступ только к разрешённым проектам

**Реализация:**
- Фильтрация данных по `enterprise_id` и `project_id` во всех запросах
- Проверка прав доступа на уровне API

### 7.2. Аутентификация и авторизация

**JWT-токены:**
- Аутентификация через Gateway-Auth Service
- Токены содержат информацию о пользователе и ролях
- Refresh tokens для обновления сессий

**RBAC:**
- Роли: энергоаудитор, администратор, разработчик
- Разрешения на уровне функций и данных

### 8.1. Оптимизация производительности

**Кэширование:**

- Уведомления о завершении операций

**Оптимизация БД:**
- Индексы на часто используемых полях
- Оптимизация запросов
- Партиционирование больших таблиц (при необходимости)

**Горизонтальное масштабирование:**
- Каждый микросервис может масштабироваться независимо
- Использование очередей для распределения нагрузки
- Load balancing на уровне Gateway

**Вертикальное масштабирование:**
- Увеличение ресурсов для отдельных сервисов при необходимости

## 10. Заключение

Архитектура EAIP спроектирована с учётом требований ТЗ:

1. **Расширяемость** — новые энергоресурсы, нормативы, шаблоны добавляются без изменения кода
2. **Независимость от шаблонов** — каноническая модель данных, шаблоны как форматы представления
3. **Мультитенантность** — работа с множеством предприятий и проектов
4. **Гибкость** — поддержка различных AI-провайдеров, шаблонов, форматов файлов
5. **Надёжность** — резервное копирование, версионирование, история изменений

Архитектура позволяет поэтапно развивать систему, добавляя новые функции без перестройки существующих компонентов.
