## 📋 РЕЗЮМЕ ПО РАЗДЕЛАМ 1-9

### Раздел 1: Назначение и цели системы EAIP

**Цель раздела:** Определить назначение системы, её цели и принцип независимости от конкретных шаблонов.

**Ключевые требования:**
- EAIP — внутренняя система для энергоаудита, расчёта потребления, формирования энергопаспорта и отчётов
- Ориентация на соответствие ПКМ-690 (Узбекистан), но без жёсткой привязки к одному шаблону
- Независимость от конкретного шаблона Excel — собственная логическая модель данных
- Цели: сокращение трудозатрат, прозрачность расчётов, минимизация ошибок, гибкость

**Технические решения:**
- Архитектура на основе доменной модели (domain-driven design)
- Абстракция слоя данных от форматов представления (Excel/Word как views, не models)
- Плагинная система для поддержки различных шаблонов отчётов

### Раздел 2: Область применения и охват энергоресурсов

**Цель раздела:** Определить пользователей системы и поддерживаемые типы энергоресурсов.

**Ключевые требования:**
- Пользователи: энергоаудиторы, инженеры, внутренние разработчики
- Поддержка работы с несколькими предприятиями и проектами
- Работа с ЛЮБЫМИ энергоресурсами (электроэнергия, газ, вода, мазут, уголь и др.)
- Расширяемый справочник энергоресурсов (не жёстко зашитый список)
- Для каждого ресурса: наименование, тип, единица измерения, коэффициент пересчёта в т.у.т.

**Технические решения:**
- Справочник ресурсов в БД с возможностью расширения через UI
- Полиморфная модель данных для различных типов ресурсов
- Конфигурируемые единицы измерения и коэффициенты пересчёта
- Мультитенантность на уровне предприятий и проектов

### Раздел 4: Функциональные требования (модули и подсистемы)

**Цель раздела:** Детально описать все функциональные модули системы.

**Ключевые требования:**

#### 4.1. Модуль администрирования и справочников
- Справочники: продукция, энергоресурсы, единицы измерения, площадки/здания, нормативы, коэффициенты
- Управление пользователями и ролями
- Управление архивом проектов

#### 4.2. Модуль управления проектами
- Создание проекта по предприятию
- Автоматическая генерация пакета документов (договор, перечень данных, инструкции)
- Учёт статуса задач по сбору данных

#### 4.3. Модуль загрузки и хранения файлов
- Поддержка: Excel, Word, PDF (текст/скан), изображения (JPG/PNG), CSV/TSV
- Привязка к проекту и типу документа
- Файловое хранилище (MinIO/S3-совместимое)
- Автоматическая опись документов

#### 4.4. Модуль OCR и интеллектуального разбора
- OCR для PDF-сканов и изображений
- Структурирование табличных данных
- Выявление сомнительных фрагментов
- Подготовка пометок для ручной проверки
- Настраиваемые пороги уверенности

#### 4.5. Модуль проверки согласованности
- Проверки: месяц=квартал=год, суммы по категориям, отсутствие деления на ноль
- Выявление аномалий
- Формирование списков ошибок, предупреждений, рекомендаций
- Интерфейс принятия решений аудитором

#### 4.6. Модуль логики энергопаспорта (7 подсистем)
1. **Продукция:** объёмы по периодам, преобразование единиц
2. **Нормы и факт:** нормативный и фактический удельный расход, отклонения
3. **Энергопотребление по продукции:** расчёт по кварталам и годам
4. **Структура потребления:** распределение по категориям (производство, потери, хоз-быт)
5. **Энергетический баланс:** агрегирование по ресурсам, пересчёт в т.у.т.
6. **Удельные показатели:** на единицу продукции и площади, сравнение с нормативами
7. **Динамика:** изменения по годам, поддержка произвольной последовательности лет

#### 4.7. Модуль формирования отчётов
- Аналитические таблицы и диаграммы
- Отчёт энергоаудита (Word)
- Энергопаспорт (Excel, ПКМ-690)
- Экспорт в PDF

#### 4.8. AI-подсистема
- Анализ документов и данных
- Обнаружение ошибок и аномалий
- Генерация предложений по корректировкам
- Генерация текстов разделов отчёта
- Генерация мероприятий по энергоэффективности
- Явное отделение предложений ИИ от данных, обязательное утверждение аудитором

#### 4.9. Журналирование и аудит
- Протоколирование действий (загрузка, изменения, расчёты)
- Фиксация автора и времени
- История изменений по проекту

**Технические решения:**
- Микросервисная архитектура (уже частично реализована)
- Event-driven архитектура для журналирования
- Плагинная система для AI-модулей
- Централизованная система расчётов (уже есть `energy_passport_calculations.py`)

### Раздел 5: Требования к данным, структуре энергопаспорта и расчётам

**Цель раздела:** Определить источники данных, порядок расчётов и проверки согласованности.

**Ключевые требования:**
- Источники: файлы предприятия, ручной ввод, нормативные справочники
- Порядок расчётов: загрузка → расчёты → формирование форм
- Проверки согласованности: суммы, отсутствие деления на ноль, аномалии
- Гибкость: количество ресурсов/продукции/лет не фиксируется в коде
- Параметризация: нормативы и коэффициенты в справочниках

**Технические решения:**
- Единая модель данных (canonical model) для всех источников
- Конфигурируемые правила валидации
- Расчётный движок с зависимостями (dependency graph)
- Версионирование нормативов и коэффициентов

**Вопросы:**
- Как именно должна выглядеть структура справочника в БД?
- Нужна ли иерархия типов ресурсов (электроэнергия → активная/реактивная)?
- Как обрабатывать ресурсы с разными единицами измерения в одном типе?
- Нужна ли валидация при добавлении нового ресурса?

**Решение (согласовано):**

1. **Каноническая сущность `EnergyResource`:**
   - Поддержка любых ресурсов: электроэнергия, газ, вода, мазут, уголь, дизель, тепло, пар, сжатый воздух и т.д.
   - Расширяемость без изменения кода через справочник в БД.

2. **Структура записи (обязательные поля):**
   - `id` — внутренний идентификатор
   - `code` — краткий код (латиницей, уникальный: `ELEC`, `GAS`, `WATER`, `MAZUT`, `COAL` и т.п.)
   - `name_ru` — полное наименование на русском
   - `resource_group` — укрупнённая группа (`electricity`, `gas`, `liquid_fuel`, `solid_fuel`, `water`, `heat`, `other`)
   - `unit_main` — основная единица учёта (кВт·ч, м³, т, Гкал и т.п.)
   - `allowed_units` — допустимые единицы ввода с коэффициентами приведения к `unit_main`
   - `k_tut` — коэффициент пересчёта в т.у.т (при наличии)
   - `is_active` — флаг активности
   - Ссылки на нормативный источник (НД, методика)

3. **Иерархия:**
   - Допускается по группе и подтипу (например: `electricity` → `active`/`reactive`/`total`)
   - Реализация через поле `subtype` или отдельную таблицу иерархии

4. **Единицы измерения:**
   - Один канонический `unit_main` для каждого ресурса
   - Остальные единицы через таблицу конвертации `EnergyResourceUnit` с коэффициентами пересчёта
   - Разные единицы не должны размножать сущности ресурсов

5. **Валидация:**
   - Добавление/изменение только через админский интерфейс
   - Проверка уникальности `code` и согласованности единиц
   - Флаг «требует утверждения» для новых ресурсов

6. **Приоритет формирования справочника:**
   - **Приоритетная задача на раннем этапе (Этап 0/Этап 1)**
   - ИИ-компонент помогает найти и собрать действующие нормативы РУз
   - ИИ подбирает кандидатов, но **ничего не добавляет в рабочий справочник без ручного подтверждения**
   - Формирование справочника выполняется с участием ИИ и обязательной ручной верификацией

### 2. Независимость от шаблона Excel

**Риск:** Текущая реализация тесно связана с шаблоном ПКМ-690.

**Вопросы:**
- Как должна выглядеть абстракция от шаблона?
- Нужна ли поддержка нескольких шаблонов одновременно?
- Как обрабатывать изменения в нормативных требованиях (новые версии ПКМ)?
- Должна ли система автоматически адаптироваться к новым структурам шаблонов?

**Решение (согласовано):**

1. **Каноническая модель данных:**
   - Основной (канонический) слой данных, отражающий: продукцию и объёмы, ресурсы и потребление, структуру, удельные показатели, динамику, энергобаланс и т.у.т.
   - Шаблон ПКМ-690 рассматривается как **один из форматов представления/выгрузки**, а не как структура БД

2. **Работа с шаблонами:**
   - **Модуль импорта** данных из конкретного шаблона Excel (ПКМ-690, версии предприятия, др.)
   - **Модуль экспорта** в шаблон ПКМ-690 (и при необходимости — в другие шаблоны)
   - Логика расчётов и хранения данных **не зависит** от выбранного шаблона

3. **Роль предоставляемых пользователем файлов:**
   - **«Очищенный» шаблон энергопаспорта** (Excel с сохранённой структурой и формулами, без данных) — используется как **образец структуры** и проверка корректности экспорта
   - **Готовый отчёт по энергоаудиту (реальный)** — это **пример**, а не нормативный стандарт:
     - для понимания формата
     - для генерации типовых текстов разделов
     - как обучающий кейс, но **не как жёсткий шаблон**

4. **Поддержка различных форматов входных данных:**
   - **Слой сопоставления (mapping)** между внешними файлами и канонической моделью
   - Возможность **добавлять новые «профили импорта»** (mapping-конфигурации) без изменения основной бизнес-логики
